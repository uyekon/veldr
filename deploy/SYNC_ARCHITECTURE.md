# 本地版与 VIP 实时同步的双轨架构

## 结论

产品不应把“是否联网”做成所有用户共用的开关，而应把资料库分成两个互不混淆的模式：**本地资料库**和**云端资料库**。两者在 App 内共用同一个 SQLite 编辑、搜索、备份与导出能力；区别只在同步授权、远程存储和实时通知。

| 模式 | 适用用户 | 数据落点 | 网络行为 | 换机/多端 |
|---|---|---|---|---|
| 本地 | 默认、一次性购买后不启用同步的用户 | 仅设备私有 SQLite 与用户导出的备份 | 不创建账号、不请求业务 API、不上传操作日志 | 通过 ZIP/Markdown 手动迁移；可主动升级到其他模式 |
| 同步密钥库 | 买断用户主动启用跨设备同步 | 服务端只保留加密操作和加密附件 | 设备用高熵同步密钥授权；API 只传密文和 cursor | 在已授权设备生成 QR/恢复短语，新设备加入前先选合并或替换 |
| VIP 云端库 | 订阅有效的用户 | 用户账号下的服务端资料库；设备继续保留 SQLite 缓存 | 离线写入本地 outbox；在线幂等上传、拉增量；推送只用于唤醒同步 | 登录同一账号，恢复购买后继续同步 |

同一台设备可以保存多个本地资料库，但一次同步任务必须只绑定一个 `library_id` 和一个授权主体。切换账号、退出登录或切换同步密钥时，必须停止旧 outbox 的上传；绝不能把本地 A 资料库的操作发送到 B 的云端库。

## 共同同步协议

1. 编辑永远先写 SQLite，并带上客户端 UUID、`version`、软删除墓碑及 `mutation_id`。
2. 已连接同步库时，再把变更写入设备本地 `sync_mutations` outbox。断网、崩溃或 API 超时不会丢失记录。
3. 客户端按顺序上传 mutation。服务器以 `(library_id, mutation_id)` 去重；响应丢失后重试只会返回同一结果，不会重复创建文章。
4. 上传成功后客户端拉取 `changes?cursor=`。WebSocket/APNs/FCM 只发送“有新 cursor”的唤醒信号，实际资料仍通过有鉴权、可分页的 HTTPS 增量接口获取。
5. 同一实体版本不一致时，服务器返回 `409 VERSION_CONFLICT` 及当前版本。客户端保留本地 outbox 和服务器版本，显示“保留本机／使用服务器／另存为副本”的明确选择；不使用静默覆盖。

附件独立于文章 mutation：先上传分块/可续传加密 blob，拿到内容哈希后才提交引用它的文章 mutation。删除先写墓碑，延迟清理 blob，防止离线旧设备把删除的内容复活。

## VIP 服务端实现

现有 `CMS_OWNER_ID` 只用于第一个 Webadmin 兼容资料库，不能作为普通 VIP 的固定 owner。公开同步前需要把 v1 路由改为从已验证会话解析主体：

```text
request access token -> auth subject -> entitlement -> library membership
                                              -> req.syncContext.libraryId / ownerId
```

建议新增或明确以下表：

- `cms_users`：账号主体；现有 Webadmin 对应第一个固定用户。
- `cms_libraries` 与 `cms_library_members`：资料库、所属/成员关系和模式（`vip_cloud` / `key_vault`）。
- `cms_devices`：设备 ID、最后活跃时间、推送 token、撤销状态；不要把明文密码或同步密钥放入表中。
- `cms_entitlements`：商店、原始交易 ID、权益状态、到期时间、验证时间。必须由服务端验证 App Store / Google Play 交易，客户端不能自行声明 VIP。
- 现有实体与 `cms_change_log` / `cms_idempotency_records`：按 `library_id`（或等价 owner）严格隔离，并建立联合唯一索引。

VIP API 的每一次读写都需要同时校验 JWT、成员关系与有效权益。订阅到期时停止远程读写和实时推送，但本地 SQLite、浏览、编辑、导出和未上传 outbox 都保留；恢复订阅后再继续。对云端数据的保留期、删除时间和导出流程需在订阅页与隐私政策中明确。

## 买断同步密钥库

同步密钥不是购买凭证，也不是短密码。第一台已购买设备生成不可枚举的 `library_id`、随机秘密和端到端加密根密钥；服务器保存密文 mutation、密文附件、cursor 和最小化配额信息。新设备扫描 QR 或输入恢复短语后才能派生密钥并加入。

服务端不能根据“忘记 key”恢复密文内容，因此产品必须在生成时提示用户保存恢复短语，并支持在仍有已授权设备时轮换密钥、撤销丢失设备。一次性购买权益仍由商店恢复；同步密钥仅决定能否访问这一份资料库。容量、设备数与长期不活跃资料库回收策略必须在售卖前确定。

## 资料库状态转换

- 本地 -> VIP：用户登录并完成权益校验后，先下载云端摘要，展示合并预览；用户确认后将本机全部内容写入 outbox，再同步，不清空本地数据库。
- 本地 -> 同步密钥库：生成密钥后采用同样的合并预览，上传内容全程先在客户端加密。
- VIP -> 本地：停止同步并保留最后一份 SQLite 副本；用户可选择删除服务器资料，服务端按保留政策执行。
- 现有 Webadmin -> App：作为首个 owner 的受限迁移入口，先 bootstrap；在双向验证完成前不得作为通用账号体系。

## 分步交付

1. **当前**：Webadmin 安全 bootstrap、设备会话、SQLite 本地 mutation outbox；默认本地用户没有任何 API 流量。队列上传器会按顺序发送支持的 mutation，成功后以服务端版本回写本地，失败或版本冲突则保留队列并停止。对于已积累大量离线数据且经确认目标云端为空的资料库，App 可原子生成全量首次上传队列，并以 Notebook、父子分类、笔记、白板的依赖顺序保存；附件会明确标记为待后续分块传输，绝不伪装成已同步。
2. Webadmin 双向验证：客户端 UUID 创建、outbox 幂等上传、版本冲突界面、cursor 增量拉取，先覆盖笔记和白板，再覆盖 Notebook/分类/附件。首次 VIP 升级时，先读取云端摘要；云端非空必须进入合并预览，不能使用“空库全量上传”路径。
3. 账号与权益：将固定 `CMS_OWNER_ID` 路由演进为资料库成员路由，接入 App Store Server API/通知与恢复购买。
4. VIP 实时：APNs/FCM + WebSocket 唤醒、后台刷新、设备管理、订阅到期降级。
5. 买断密钥库：端到端加密、QR/恢复短语、密钥轮换、配额与回收；单独安全审计后再开放。

这条顺序确保任何阶段的默认用户都只是本地使用；只有用户主动连接或登录、且界面明确说明数据去向后，才会开始远程同步。
